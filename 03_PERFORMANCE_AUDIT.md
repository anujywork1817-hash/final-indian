# 03 — Performance Audit

## Status: no baseline exists yet

There is **no existing load test in the repository** (no k6, no locust, no artillery script found), and **no CI** to have run one automatically. This audit is therefore a static/code-review-based performance risk assessment, not a measured one. Measured numbers come in Phase 2 (`PERFORMANCE_BASELINE.md`), after this audit and after security hardening — per the master prompt's own phase ordering, do not load-test an insecure system and call the result meaningful.

## Known/likely hotspots from the verified architecture (to confirm with `EXPLAIN ANALYZE` in Phase 5, not assumed)

1. **Booking creation path holds a row lock across a multi-step transaction**: `SELECT ... FOR UPDATE` on the tent row, followed by a count query over overlapping bookings, followed by the insert, all in one transaction. This is *correct* for preventing overbooking, but it means every concurrent booking attempt for the *same tent* serializes on that lock. At 10k concurrent users this is fine in aggregate (most users book different tents/date ranges) but will show up as elevated P99 latency and potential lock-wait timeouts specifically for **popular tents on popular dates** — exactly the peak-Kumbh-surge scenario the app's own domain model anticipates. This needs a targeted load-test scenario (many concurrent bookings against one tent), not just aggregate RPS.
2. **api-gateway's `proxy()` reads the entire request body into memory before forwarding.** For the endpoints in this app (small JSON payloads, no bulk uploads observed) this is low-risk, but it means there is currently no per-request payload size cap enforced before that read — an oversized request body could be a memory-pressure vector under concurrent load. Needs a `MaxBytesReader`-equivalent cap.
3. **Every service connects to the same single Postgres instance with no documented pool tuning.** Five independently-scaled service types × N replicas each, all against one `max_connections` ceiling, is the single most likely cause of "works at 1,000 users, falls over at 5,000" — this is the textbook connection-storm failure mode the master prompt calls out in §11. Must be measured and explicitly capped per §11's formula (instances × per-instance pool ≤ DB capacity) before any horizontal scale-out.
4. **In-process cron duplication under replication** (see architecture audit) is a correctness bug, but also a load-generation bug: N replicas of `booking-service` means N× the daily reminder/cleanup query load and N× the outbound FCM calls, for no benefit. This inflates DB and external-API load in direct proportion to replica count — the opposite of what horizontal scaling should do.
5. **No caching layer of any kind** (no Redis, no in-memory cache with TTL, no HTTP caching headers observed). `GET /tents` (tent catalogue browse — almost certainly the single highest-traffic read endpoint in a booking app) hits Postgres on every single request from every user, with no cache. This is the highest-value caching target once Redis is introduced.
6. **N+1 query risk — CONFIRMED CLEAR.** Direct source read of `tent-service/handler.go:57-79` (`listTents`) confirms a single query using `LEFT JOIN bookings ... GROUP BY t.id` to compute availability — correct, no N+1. `booking-service/handler.go`'s data-fetch sites all use single-query + scan-loop patterns, no per-row query issued inside a result-set loop. The only inefficiency found is the admin stats endpoint (`booking-service/handler.go:819-822`) issuing four sequential `db.QueryRow` calls for separate aggregates where one CTE could do it in one round-trip — minor, not a correctness or scale risk at this traffic level, low-priority cleanup only.
7. **External API calls — CONFIRMED bounded, but with no retry/backoff/circuit-breaker.** `payment-service/handler.go:80` and `payment-service/orders.go:80` both use `&http.Client{Timeout: 10 * time.Second}`. `booking-service/refunds.go:169` uses a configurable timeout (`REFUND_GATEWAY_TIMEOUT_SECONDS`, default 20s). `api-gateway/main.go:229`'s `proxy()` uses `&http.Client{Timeout: 30 * time.Second}` for gateway→internal-service calls. So no request can hang forever — good. But none of these use exponential backoff, jitter, or a circuit breaker; the refund path instead relies on its own DB-tracked attempts/interval retry worker, which is an acceptable substitute for that one flow but does not exist for order-creation or gateway-proxy calls. Under a Razorpay outage, every in-flight `/orders/create` call will simply time out after 10s and return an error per-request — not catastrophic, but will spike P99 latency and consume a connection slot for the full 10s per attempt at scale. Circuit-breaking `payment-service`'s Razorpay calls (fail fast after N consecutive timeouts, recover on a cooldown) is a legitimate Phase 4 addition, not urgent for initial hardening.
8. **No `http.Server` timeouts, no graceful shutdown — CONFIRMED across all five services and `cmd/`.** Every service calls `gin.Default()` then `r.Run(":" + port)`, which is Gin's shorthand for `http.ListenAndServe` with zero custom `http.Server{}` config. There is no `ReadTimeout`/`WriteTimeout`/`IdleTimeout`, and no `signal.Notify` + `.Shutdown(ctx)` anywhere in the module (confirmed by grep — zero matches). Two separate consequences: (a) slow/stalled client connections have no server-side timeout protection, a resource-exhaustion vector under adversarial or just very slow-network load; (b) rolling deploys / autoscale-in events will hard-kill in-flight requests rather than draining them, directly violating master-prompt §6 and §29 (zero-downtime deploy). **This is a required Phase 4 fix, not optional**, since it blocks safe horizontal autoscaling and rolling deploys outright, independent of the 10k-user question.

## What load testing must distinguish (per master prompt §34)

Given the current infra (local dev machine, no cloud environment provisioned for this audit), any load test run right now would be testing the **load generator and a laptop-class Postgres container**, not a production topology. This must be stated explicitly rather than producing a number that gets misquoted as "the system supports X users." See the final status block for the BLOCKED declaration on 10k-user testing.
